# 容量评估（M9）

> 数据来自 `scripts/loadtest.py`，在**本机**（Windows / SSD / Python 3.12 / 单进程）跑出来。
> 它测的是**编排层**开销（历史读写 + 上下文裁剪 + 工具执行 + 观察者写入），
> 用的是确定性模型，**不含模型调用**——真实延迟由上游模型决定，换一天就变。

```powershell
uv run python scripts/loadtest.py --concurrency 16 --turns 10                 # 内存
uv run python scripts/loadtest.py --concurrency 16 --turns 10 --database      # SQLite
uv run python scripts/loadtest.py --concurrency 16 --turns 10 --no-tool       # 不带工具
```

每轮都是「模型 → 调 `now` 工具 → 模型 → 结论」两次模型往返、一次工具调用。

## 1. 结果

| 配置 | 并发×轮数 | 吞吐 (轮/秒) | p50 | p95 | 被拒 |
| --- | --- | --- | --- | --- | --- |
| 内存历史 + 工具 | 16 × 10 | **168.9** | 88.6 ms | 224.8 ms | 0 |
| 内存历史，无工具 | 16 × 10 | **345.4** | 28.1 ms | 223.4 ms | 0 |
| 内存历史 + 工具 | 64 × 5 | **188.9** | 303.4 ms | 407.5 ms | 0 |
| SQLite 历史（改前） | 16 × 10 | **6.0** | 2432 ms | 3578 ms | 0 |
| SQLite 历史（改后） | 16 × 10 | **9.6** | 1491 ms | 2276 ms | 0 |
| SQLite 历史，64 并发 | 64 × 5 | 13.5 | 4642 ms | 5370 ms | 0 |

## 2. 结论

**编排层不是瓶颈。** 内存模式下 16 并发跑到 169 轮/秒、p50 约 90 ms；
真实场景里模型一次要 1–3 秒，编排占其中不到 10%。
**瓶颈是 SQLite。** 落库时同样的负载掉到 9.6 轮/秒、p50 1.5 秒 —— 这是 20 倍的落差。

## 3. 为什么 SQLite 这么慢（逐层量出来的）

用三个一次性基准脚本逐层剥离（`SELECT 1` 绕过所有仓储代码）：

| 操作 | 1 并发 | 16 并发 |
| --- | --- | --- |
| `SELECT 1` + commit | 1.35 ms / 条，446 条/秒 | 21.8 ms / 条，**427 条/秒** |
| 只取连接（不执行语句） | 0.10 ms | 2.2 ms |
| 历史 `load`（30 条消息） | — | 113 ms |
| 历史 `append` | — | 60 ms |
| `get_thread` | — | 149 ms |
| 三者合计（一轮） | — | 124 ms |

两个事实：

1. **每条语句有 ~1.4 ms 的固定成本**。这远高于 SQLite 应有的水平，
   来源是 `aiosqlite` 的模型：每个连接一个专属线程，
   每条语句都要「事件循环 → 线程 → 事件循环」跑一趟，
   再加上 SQLAlchemy 的会话与提交簿记。
2. **总吞吐封顶在 ~450 条语句/秒**，与连接池大小**无关**——
   试过 `size=5` / `size=16` / `size=1`，16 并发下都是 400–550 条/秒。
   也就是说这不是「池子太小」，而是**语句执行路径本身的串行成本**。

一轮运行要 3 次语句（`load` + `append` + `get_thread`），加上审计与用量写入，
于是 `450 ÷ 5 ≈ 90` 轮/秒是理论上限，而实测 9.6 —— 差额来自读写混合时
SQLite 的写锁与 `append` 的提交（WAL 下仍然串行）。

## 4. 据此做的改动

| 改动 | 效果 | 位置 |
| --- | --- | --- |
| `journal_mode=WAL` | 读不再被写阻塞 | `storage/database.py` |
| `synchronous=NORMAL` | 提交不再每次 fsync（WAL 下安全） | 同上 |
| `busy_timeout=5000` | 撞锁时等待，而不是立刻 `database is locked` | 同上 |
| 审计写后缓冲（默认 50 条一批） | 一轮的提交从 ~5 次降到 ~1 次 | `observability/buffering.py` |
| 用量写后缓冲 | 顺带减少「读改写」往返 | 同上 |

合计把 SQLite 模式从 **6.0 提到 9.6 轮/秒**（+60%），磁盘写入次数显著下降。
**但没有改变量级** —— 因为瓶颈不在提交次数，而在语句执行路径。

攒批的代价必须说清楚：进程被 `SIGKILL` 时可能丢掉最后不足 `batch_size` 条的
审计与用量记录。读接口（`/audit`、`/usage`）会**先 flush 再查**，
所以「刚发生的查不到」不会发生。要严格逐条持久化就把 `batch_size` 设成 1。

## 5. 容量建议

| 场景 | 建议 |
| --- | --- |
| 单用户 / 个人使用 | 默认配置够用。SQLite 的 9.6 轮/秒 远超一个人的提问速度 |
| 小团队（几人共用） | 把 `storage.history` 保持 `database`（数据要能回溯），接受 p50 秒级；`batch_size` 可调大 |
| 高并发 / 多副本 | **必须换外部数据库**（Postgres）。SQLite 的单写者模型是硬上限，调参解决不了 |
| 演示 / 压测 / CI | `storage.history: memory`，170 轮/秒且无磁盘 IO |
| 从 SQLite 迁移 | 数据在单文件里，`threads`/`messages` 可直接导出；换库后记得复核 `approvals` 与 `audit_events` 的保留策略 |

## 6. 还没有测的

* **真实模型下的端到端延迟**：那由上游决定，本机测不出有意义的数字；
* **多副本**：`gateway.session` 的锁是进程内的，本轮没做多副本（见 roadmap M9 的范围）；
* **长期运行的资源增长**：审计表有 `max_rows` 上限、用量表按天聚合，
  但上下文摘要与卸载目录的增长没有做专门的长期观测。

**这些是已知空白，不是「已经没问题」** —— 写在这里，免得下一个人以为测过了。
